## 4. 需求分析

### 4.1 项目目标

实现一个论文查重程序：输入原文文件与抄袭版论文文件（均为文件路径），程序计算两者之间的重复率，并将结果写入答案文件。

### 4.2 功能需求（FR）

| 编号 | 需求       | 说明 / 验收标准                                              |
| ---- | ---------- | ------------------------------------------------------------ |
| FR-1 | 命令行参数 | 程序通过命令行接收三个绝对路径参数：原文文件、抄袭版论文文件、答案文件；参数以空格分隔，路径中不含空格。调用形式：Python `python main.py [原文文件] [抄袭版论文的文件] [答案文件]`；C `main.exe ...`；Java `java -jar main.jar ...` |
| FR-2 | 文件读取   | 从指定路径读取原文与抄袭版论文文件内容（含样例 orig.txt、orig_add.txt 等抄袭版论文） |
| FR-3 | 查重算法   | 设计论文查重算法，针对"在原文上经过增删改的抄袭版论文"计算重复率 |
| FR-4 | 结果输出   | 将重复率以浮点型写入答案文件，精确到小数点后两位             |
| FR-5 | 语言与入口 | 使用 C++ / Java / Python3 之一实现；Python 入口文件为 main.py 并附 requirements.txt；C/C++ 提供可执行文件 main.exe（VS2017、64-bit Windows 10）；Java 提供编译好的 jar 包 main.jar |
| FR-6 | 发布       | C++/Java 需将编译好的程序发布到 GitHub 仓库的 releases 中    |
| FR-7 | 异常处理   | 对各类异常（如文件不存在等）进行处理，程序不得异常退出（详见 4.5） |

### 4.3 非功能需求（NFR）

| 编号  | 需求         | 指标                                                         |
| ----- | ------------ | ------------------------------------------------------------ |
| NFR-1 | 响应时间     | 5 秒内给出答案                                               |
| NFR-2 | 内存占用     | 不超过 2048MB                                                |
| NFR-3 | 内存安全     | 无严重内存泄漏                                               |
| NFR-4 | 运行稳定性   | 评测过程中不发生异常退出                                     |
| NFR-5 | 代码质量     | 通过 Code Quality Analysis 工具分析并消除所有警告            |
| NFR-6 | 可读性与命名 | 代码有注释、可读性好；变量、函数、类命名规范化               |
| NFR-7 | 可复现编译   | 源代码可正常编译，并能编译出与提交可执行文件逻辑相同的可执行文件 |

### 4.4 工程过程需求（PR）

| 编号 | 需求            | 要求                                                         |
| ---- | --------------- | ------------------------------------------------------------ |
| PR-1 | GitHub 源码管理 | 仓库中新建以学号为名的文件夹；代码有进展即签入；按功能划分，每完成一个功能且编译成功后至少 commit 一次，至少区分"基本功能"与"扩展功能"，总共至少 commit 两次 |
| PR-2 | PSP 表格        | 开始实现前记录各模块预估耗时；实现完成后记录各模块实际耗时   |
| PR-3 | 性能分析        | 完成首个版本后，使用性能分析工具（VS 2017 Studio Profiling Tools / JProfiler）找出性能瓶颈并改进 |
| PR-4 | 单元测试        | 编写至少 10 个测试用例；至少采用白盒测试用例设计方法；使用插件查看测试分支覆盖率等指标；单元测试需自动化，便于随时运行 |
| PR-5 | 博客            | 博客正文首行给出作业 GitHub 链接，并按博客评分规则撰写各章节 |

| 编号 | 约束                                           | 后果                                                         |

| CR-1 | 禁止尝试连接网络                               | 作业以 0 分计                                                |

| CR-3 | 禁止尝试妨碍评测（例如 system("shutdown")）    | 作业以 0 分计                                                |

### 4.6 需求边界与待确认事项

- 原文未指定具体查重算法，由学生自行设计，并在博客中说明算法关键与独到之处；
- 原文未指定文件编码格式（如 UTF-8 / GBK），实现时需自行确定并保持读取处理一致；
- 原文未明确空文件、非法路径、超大文件、单行超长文本等边界场景的处理口径，建议实现前确定，并在异常处理说明中给出对应单元测试样例；
- 重复率输出为浮点型、精确到小数点后两位，建议统一采用固定两位小数格式（如 `%.2f`）输出。

## 5. 测试需求整理

### 5.1 评测方式（功能测试）

- 评测通过命令行参数传入三个文件路径（路径不含空格），程序从指定位置读取文件并向指定文件输出答案；
- 共有 18 个测试点（不含样例）；
- 样例：orig.txt 为原文，orig_add.txt 等为抄袭版论文。

### 5.2 测试点不通过情形（每个不通过测试点扣 2 分）

| 情形                  | 说明                 |
| --------------------- | -------------------- |
| 程序内存泄漏严重      | 资源管理存在严重问题 |
| 5 秒内未给出答案      | 响应超时             |
| 占用的内存超过 2048MB | 内存超限             |
| 发生异常退出          | 进程崩溃或非正常结束 |

### 5.3 单元测试要求

- 至少 10 个测试用例，确保程序能正确处理各种情况；
- 至少采用白盒测试用例设计方法（其他方法不限）；
- 使用插件查看测试分支覆盖率等指标；
- 单元测试需自动化，可在每台机器上随时运行（如每日构建中运行）；
- 结合测试评估要求，评价测试设计能否满足该程序的测试要求。
